# 개념기반탐구학습지 설계·집필 규칙

## 왜 이 형식인가
설명을 읽는 수업은 "SRP는 변경 이유가 하나"를 외우게 하지만, 학생이 변경의 고통을 직접 겪고 스스로 규칙을 말해 보게 하면 새 상황에서도 원칙을 적용한다(전이). 그래서 학습지는 **교사 설명을 최소화하고 학생이 사실 → 개념 → 일반화 → 전이로 올라가게** 설계한다.

## 3차시 구성 (각 45~50분)
| 차시 | 개념적 렌즈 | 원칙 | 핵심 일반화(학생이 스스로 진술) |
|------|-----------|------|-----------------------------|
| 1 | 변경(Change) | SRP, OCP | 코드는 변경 이유별로 나눌 때, 새 요구를 기존 코드 수정 없이 추가로 흡수할 수 있다 |
| 2 | 약속(Contract) | LSP, ISP | 타입 관계는 문법이 아니라 행동 약속이며, 약속은 사용자가 필요한 만큼만 작아야 지킬 수 있다 |
| 3 | 의존(Dependency) | DIP + 종합 | 의존 방향을 추상으로 돌리면 변경이 전파되지 않으며, 원칙은 균형 있게 적용해야 한다 |

OOP 복습(추상화·상속·다형성·ABC)은 별도 차시 없이 1차시 도입 "워밍업" 5~8분과 사전 읽기(`chapter_00`)로 처리한다.

## 차시 내부 흐름 (탐구 순환)
1. **연결(5분)** 주제 상황 제시 + 렌즈 질문. 학생의 선개념을 한 줄로 적게 한다(사전 생각).
2. **조사(15분)** 예측-실행-관찰: 학생이 나쁜 코드를 읽고 "요구가 바뀌면 어디를 고칠까?"를 **먼저 예측**하고, 시작 코드를 직접 실행·수정해 결과를 기록한다.
3. **조직(10분)** 사례 분류/카드 정렬/표 완성/짝 토론으로 패턴을 찾는다.
4. **일반화(8분)** 빈칸 없이 자기 말로 원칙 문장을 쓰고, 모둠 문장을 합친다. 정의는 학생 진술 **이후**에 공개된다(교사 가이드의 확인 멘트).
5. **전이·성찰(7분)** 낯선 도메인의 코드에 적용 + 퇴장권(exit ticket) + 자기 점검 + 과잉 적용 경계 질문.

## 질문의 세 층위 (Erickson)
- 사실적: 이 코드에서 클래스가 몇 가지 일을 하는가?
- 개념적: 변경 이유가 다르다는 것은 무슨 뜻일까? 두 코드의 차이를 설명하는 일반적 규칙은?
- 논쟁적: 모든 if문을 클래스로 바꾸는 것이 항상 좋은가?
차시마다 세 층위를 모두 최소 1개씩 포함한다.

## 활동 유형 (차시당 최소 5종 사용, 서로 다른 인지 행동)
예측하기 / 코드 실행·관찰 기록 / 코드 직접 수정(TODO 채우기) / 사례 카드 분류 / 짝 코드 리뷰 / 찬반·논쟁 / 자기 말로 일반화 / 낯선 도메인 전이 / 오개념 반박(틀린 학생 진술 고치기) / 퇴장권·자기 점검.

## 학습지(HTML) 규칙
- 파일: `solid_course/worksheets/session_N.html`, 공통 `assets/style.css`·`assets/worksheet.css`·`assets/worksheet.js` 상대경로 링크, 외부 CDN 금지(단, 파이썬 편집기가 쓰는 Pyodide는 예외: `assets/pyedit.js`가 jsDelivr 고정 버전을 Web Worker로 불러온다).
- 활동은 `<section class="activity" data-type="predict|observe|code|sort|pair|debate|generalize|transfer|reflect">` 로 번호(활동 1-1…) 매기고 모두 `<textarea>`/선택지/표 입력칸을 둔다. 입력은 localStorage 자동 저장(`worksheet.js`), 인쇄(A4) 시 입력칸 높이·테두리 유지.
- **학습지에 정답·힌트 해설을 절대 넣지 않는다.** 막힌 학생용 힌트는 `<details class="hint">` 단계 힌트(1단계 방향, 2단계 구조)까지만, 정답 코드는 금지.
- 각 활동에 예상 시간, 활동 형태(개인/짝/모둠), 대응 학습목표 번호를 표기.
- 개념 박스(`box concept`)는 학생 일반화 **이후 구역**에 정의 확인용으로만 두고, `<details class="defs">`로 접어 학생이 문장을 쓴 뒤 열게 한다. 제목·lead·목표에도 원칙 이름과 전문 용어를 일반화 이전에 노출하지 않는다.
- 시작 코드: `solid_course/worksheets/code/sN_*.py`. 표준 라이브러리만, Python 3.12+, `# TODO(학생)` 마커, 실행하면 현재 상태 출력(실패 테스트는 `assert` 메시지로 안내). 코드에 정답을 두지 않는다. 미완성이어도 exit 0 + `[미완성]` 안내로 끝낸다.
- **점검 로직은 오답 우회를 시험한다**: 학생 코드를 일부러 틀리게(구체 타입 힌트, 빈 Protocol, 내부 생성 등) 바꿔 점검이 통과하지 않는지 확인한다. 학생이 주석 지시대로 코드를 놓았을 때 NameError가 나지 않도록 정의 위치(TODO 순서)도 실행해 확인한다.

## 오개념 주의 (정확성)
solid-lesson-writing의 "원칙별 오해 주의"를 그대로 따른다. 특히 SRP=메서드 1개 아님, OCP=무조건 확장점 아님, LSP=상속 문법이 아닌 행동 계약, DIP≠DI 기법 자체.

## 코드 신택스 하이라이팅 (필수)

학습지에 나오는 **모든 파이썬 코드는 신택스 하이라이팅**이 되어야 한다. 색 없는 코드 블록을 만들지 않는다.

- 본문 코드는 `<pre><code>…</code></pre>`로 쓴다(`<`,`>`,`&` 이스케이프). 공용 `assets/highlight.js`가 로드 시 모든 `pre > code`를 자동으로 칠하므로 학습지는 `highlight.js`를 `pyedit.js`보다 먼저 불러온다. 파이썬이 아닌 블록(실행 결과·그림)은 `<code class="out">`으로 표시해 건너뛴다. 별도 클래스·수동 `<span>`은 쓰지 않는다.
- 줄 번호가 붙은 블록(`25  class …`)은 줄 번호를 코드와 두 칸 띄워 쓴다. 번호는 자동으로 흐리게 처리된다(빈 줄은 번호만 있어도 된다).
- 편집기(`.pyedit`)·💡 예시 코드 팝업도 같은 규칙으로 칠해진다. 새 코드 표시 UI를 만들면 `highlight()`를 거치게 한다.
- 색은 `highlight.js`가 넣는 `--tk-*` 변수(라이트/다크)로만 바꾼다. `--tk-*` 변수와 토큰 규칙(`KW`, `BUILTIN`, `TOKEN`)은 `highlight.js`에 있다.
- 새 학습지를 만들거나 코드를 고친 뒤에는 브라우저(또는 헤드리스 Chrome)로 열어 `tk-` 클래스가 적용됐는지 확인한다.

## 디자인 시스템 (필수)
- 모든 학습지·교재·평가 화면은 `solid_course/assets/tokens.css`의 **디자인 토큰**과 `style.css`(공통)·`worksheet.css`(학습지) 컴포넌트를 쓴다. 규칙 문서는 `solid_course/design-system.html`.
- 컴포넌트 CSS에는 `#hex`·임의 `px`를 쓰지 않고 `var(--…)` 토큰만 쓴다(다크 모드·인쇄 자동 대응). 새 값이 필요하면 `tokens.css`에 토큰을 먼저 추가한다.
- 활동 카드는 `.activity[data-type=…]`(윗띠 색 = 활동 유형), 질문 수준은 `.q-level.fact|concept|debate`, 강조는 `.box.concept|tip|warn`·`.situation`·`.lens`를 재사용한다. 새 클래스를 만들기 전에 기존 컴포넌트로 되는지 본다.
- 한 화면에 채워진(주) 버튼은 하나만 둔다. 색만으로 의미를 전달하지 않는다(배지에 글자). 스타일을 바꾼 뒤 라이트·다크·모바일(≤720px)·인쇄를 확인한다.
