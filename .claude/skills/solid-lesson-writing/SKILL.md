# SOLID 수업자료 집필 규칙

## 장 구조 (순서 고정)
1. **학습목표** (2~3개, 측정 가능한 동사)
2. **개념** — 원칙 한 문장 정의 + 왜 필요한가
3. **상황** — 위반의 고통이 느껴지는 구체적 시나리오 (요구사항이 바뀌는 순간 포함)
4. **나쁜 코드** — 실행은 되지만 설계가 나쁜 코드 + 무엇이 문제인지 번호 주석
5. **개선 코드** — 원칙 적용 + 같은 요구 변경을 이제 어떻게 흡수하는지
6. **정리** — 한눈에 비교표, 흔한 오해, 과잉 적용 주의
7. **이해 점검** — 장 하단 `<section class="quiz">` (규칙은 `solid-quiz-design`)

## 출력 형식: HTML
- 장마다 단일 파일 `solid_course/chapter_NN_*.html`. 공통 `assets/style.css`, `assets/quiz.js`를 상대경로로 링크한다(외부 CDN 금지, 오프라인 동작).
- `<html lang="ko">`, viewport meta, 시맨틱 태그(`header/main/section/aside/nav`) 사용. 상단 nav에 index와 이전/다음 장 링크.
- 코드는 `solid_course/code/chapter_NN_*.py`와 **동일한 내용**을 `<pre><code class="bad|good">`에 넣는다(`<`,`>`,`&` 이스케이프). 나쁜 코드는 `bad`, 개선 코드는 `good` 클래스.

## 박스 설명란 규격
새 개념/용어가 처음 나오면 개념 박스를 개념이 나온 지점 바로 아래에 둔다.

```html
<aside class="box concept">
  <h4>📦 새 개념: 추상 클래스 (ABC)</h4>
  <ul>
    <li><b>정의</b>: 직접 인스턴스를 만들 수 없고 하위 클래스가 구현할 메서드를 강제하는 클래스</li>
    <li><b>왜 필요?</b>: 공통 약속(인터페이스)을 코드로 못 박기 위해</li>
    <li><b>예</b>: <code>class Shape(ABC): ...</code></li>
  </ul>
</aside>
```

보조 박스: `box tip`(💡 핵심 포인트), `box warn`(⚠️ 흔한 오해). 개념 박스는 새 개념일 때만, 남발 금지.

## 코드 주석 규칙
- 파일 상단 docstring: 목적, 어떤 원칙을 다루는지, 실행 방법
- `# [문제 1]` / `# [해결 1]`처럼 번호를 달아 본문 설명과 연결
- "무엇"이 아니라 "왜"를 쓴다. 요구가 바뀌면 어느 줄을 고쳐야 하는지 밝힌다.
- 파일 하단 `if __name__ == "__main__":` 에 데모를 두고, 출력으로 동작을 확인 가능하게 한다.
- 파이썬 3.10+ 문법, 타입 힌트 사용, 외부 라이브러리 금지(표준 라이브러리만).

## 원칙별 오해 주의 (정확성)
- SRP: "메서드 하나=책임 하나"가 아니라 "변경 이유가 하나"
- OCP: 모든 곳에 확장점을 두라는 뜻이 아님. 변경이 실제 반복되는 곳에만
- LSP: 하위 타입이 상위 타입의 계약(사전/사후조건, 불변식)을 깨면 안 됨
- ISP: 클라이언트별로 작은 인터페이스. 파이썬에서는 Protocol/ABC로 표현
- DIP: 고수준이 저수준 구현이 아닌 추상에 의존. DI(주입)는 이를 달성하는 기법
